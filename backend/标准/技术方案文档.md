## 2. 系统架构设计

### 2.1 后台在整体中的位置

```
                    ┌─────────────────┐
                    │   客户端/前端   │
                    └────────┬────────┘
                             │ HTTP/HTTPS
                             ▼
        ┌────────────────────────────────────┐
        │     Nginx 反向代理（可选）          │
        │  - API 请求转发                    │
        │  - SSL/TLS 终止                    │
        └────────────────────┬──────────────┘
                              │
                    ┌─────────▼─────────┐
                    │   Flask 后端 API  │
                    │   (Gunicorn)      │
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │     MySQL 8       │
                    │   （主数据库）     │
                    └───────────────────┘
```

### 2.2 架构层次（后台）

#### 2.2.1 应用层（Application Layer）
- **后端 API**：Flask 提供 RESTful API
- **职责**：业务逻辑处理、数据验证、权限控制

#### 2.2.2 服务层（Service Layer）
- **业务服务**：账套管理、数据导入、数据验证、数据查询
- **职责**：核心业务逻辑封装

#### 2.2.3 数据访问层（Data Access Layer）
- **ORM**：SQLAlchemy
- **职责**：数据库操作、事务管理

#### 2.2.4 数据存储层（Data Storage Layer）
- **MySQL 8**：主数据库
- **职责**：数据持久化

### 3.2 核心模块设计

#### 3.2.1 数据模型层（Models）
- **职责**：定义数据库表结构和 ORM 映射
- **主要模型**：
  - `AccountBook`：账套信息
  - `ShareArchive`：公共档案数据（科目、机构、人员等）
  - `GLData`：总账数据（凭证、分录、余额）
  - `ImportHistory`：导入历史记录
  - `User`：用户信息
  - `Role`：角色权限

#### 3.2.2 API 路由层（API / Routes）
- **职责**：定义 RESTful API 端点，处理 HTTP 请求
- **建议**：使用 `/api/v1/` 前缀做版本化
- **主要 API 模块**：
  - 账套管理：创建、查询、编辑、删除账套
  - 数据导入：公共档案导入、总账导入、批量导入
  - 数据查询：账套查询、公共档案查询、总账查询、跨账套查询
  - 数据导出：按条件导出数据
  - 数据验证：文件格式验证、数据完整性验证、逻辑验证
  - 系统管理：用户管理、权限管理、日志管理
- **认证**：基于 PyJWT 的 Token 签发与校验（无 Flask-JWT-Extended 时自行封装中间件/装饰器）

#### 3.2.3 业务服务层（Services）
- **职责**：封装核心业务逻辑，独立于 API 层
- **主要服务**：
  - `AccountBookService`：账套业务逻辑
  - `ImportService`：数据导入业务逻辑（XML 解析、数据入库）
  - `ValidationService`：数据验证业务逻辑
  - `QueryService`：数据查询业务逻辑（支持多年度查询）
  - `ExportService`：数据导出业务逻辑
  - `XMLParser`：XML 文件解析与校验（Python 标准库 `xml.etree` 或可选 lxml）

#### 3.2.4 工具层（Utils）
- **职责**：通用工具函数与辅助类
- **主要工具**：
  - 响应格式化
  - 异常处理
  - 数据验证器
  - 权限/认证装饰器（结合 PyJWT）
  - 日期/金额格式化

### 3.3 技术特性

#### 3.3.1 多年度数据管理
- **设计要点**：
  - 业务表增加 `fiscal_year`（会计年度）字段
  - 查询支持按年度筛选与多年度查询
  - 账套表维护已导入年度列表

#### 3.3.2 数据导入处理
- **流程**：
  1. 文件上传 → 临时存储
  2. XML 格式验证 → 基础格式检查
  3. 数据解析 → 解析 XML 到内存对象
  4. 数据验证 → 完整性、格式、逻辑验证
  5. 数据入库 → 事务性批量插入
  6. 结果反馈 → 返回导入结果报告

#### 3.3.3 性能优化
- **数据库**：
  - 关键字段建立索引（账套编码、会计年度、科目编号等）
  - 分页查询、批量插入优化
- **部署**：
  - 生产环境使用 Gunicorn 多进程/多 worker，按需配合 Nginx 反向代理

## 4. 数据库设计

### 4.1 数据库选型
- **主数据库**：MySQL 8.0+

### 4.2 数据库设计原则
- **多年度**：业务表增加 `fiscal_year` 字段
- **账套隔离**：业务表关联 `account_book_code`（账套编码）
- **索引**：关键查询字段建立索引
- **完整性**：外键、非空等约束

### 4.3 核心数据表（概念设计）

#### 4.3.1 系统管理表
- `sys_user`：用户表
- `sys_role`：角色表
- `sys_permission`：权限表
- `sys_user_role`：用户角色关联
- `sys_role_permission`：角色权限关联
- `sys_operation_log`：操作日志表

#### 4.3.2 账套管理表
- `account_book`：账套表（账套编码、名称、会计核算单位、组织机构代码等；已导入年度列表可用 JSON 或关联表）

#### 4.3.3 公共档案表
- `share_electronic_account_book`、`share_accounting_period`、`share_internal_organization`、`share_account`、`share_account_auxiliary`、`share_currency`、`share_exchange_rate`、`share_project`、`share_department`、`share_employee`、`share_unit`、`share_personal` 等（含年度字段）

#### 4.3.4 总账数据表
- `gl_voucher_type`、`gl_voucher`、`gl_voucher_entry`、`gl_account_balance`（含年度、期间）

#### 4.3.5 导入管理表
- `import_history`：导入历史（账套编码、文件名称、类型、会计年度、导入时间、状态、记录数等）

### 4.4 索引设计
- **账套表**：`account_book_code`（主键）
- **业务表**：`account_book_code + fiscal_year` 联合索引
- **查询表**：`account_book_code + fiscal_year + period_number` 联合索引
- **凭证/科目**：按查询条件设置 `voucher_number + fiscal_year`、`account_code + fiscal_year` 等索引

- **开发环境**：Flask 内置服务器（`flask run`）

- **后端容器**：Python 镜像 + Flask 应用 + Gunicorn
- **数据库容器**：MySQL 8
- **Docker Compose**：编排后端与 MySQL，统一网络与数据卷

## 6. 技术实现要点

### 6.1 多年度数据管理
- **存储**：业务表 `fiscal_year` 字段及 `account_book_code + fiscal_year` 联合索引
- **查询**：单年度 `WHERE fiscal_year = ?`；多年度 `WHERE fiscal_year IN (...)` 或 `BETWEEN`
- **导入**：从 XML（如电子账簿）读取会计年度，校验后写入并维护账套已导入年度

### 6.2 XML 数据处理
- **解析**：Python 标准库 `xml.etree.ElementTree` 或可选 `lxml`（当前 requirements.txt 未包含 lxml，可按需追加）
- **验证**：格式校验与业务规则校验（必填、格式、逻辑、关联）
- **转换与入库**：XML → 内存对象 → ORM 批量插入，全程事务保证一致性

### 6.3 性能优化
- **数据库**：索引、避免 N+1、批量操作、分页
- **应用**：Gunicorn 多 worker、合理超时与连接数

### 6.4 安全性
- **身份认证**：PyJWT 签发与校验 Access Token（及可选 Refresh Token）
- **权限控制**：RBAC，接口与数据权限（如按账套）
- **数据安全**：ORM 参数化防 SQL 注入；文件上传类型与大小校验

### 6.5 错误处理与日志
- **统一异常处理**：全局捕获，统一错误响应结构
- **日志**：按级别输出，文件轮转；关键操作写操作日志表

## 7. 开发规范

## 8. 总结

本技术方案针对**会计核算数据引入平台后台**，与项目 `requirements.txt` 保持一致，不涉及前端技术栈。要点如下：

1. **技术栈**：Flask 3.x + Flask-SQLAlchemy + SQLAlchemy 2.x + PyMySQL + Flask-Migrate（Alembic）+ PyJWT + python-dotenv + Pillow + Gunicorn + pytest + requests 等，见 1.1 节。
2. **多年度**：业务表年度字段与索引设计，支持多年度数据共存与查询。
3. **分层架构**：API → Service → Model，配合 Utils，结构清晰。
4. **认证与安全**：PyJWT 实现无状态认证，RBAC 与数据权限，ORM 与上传安全措施。
5. **部署**：开发用 Flask 内置服务器，生产用 Gunicorn，可选 Nginx、Docker/Docker Compose。

本文档为后台设计与实现的依据，后续若增加依赖（如 lxml、Redis、Celery 等），可在本文档中同步补充说明。
